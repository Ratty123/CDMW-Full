# Changelog

All notable changes to this project should be documented in this file.

The format is intentionally simple:

- `Added` for new features
- `Changed` for behavior or workflow changes
- `Fixed` for bug fixes
- `Docs` for README, guide, or release-note changes

## [Unreleased]

### Fixed
- Cracked the last `.papr` holdout. `cd_m0001_00_circusmachine_boss` found 236 entry starts against a declared 237 and had been rejected rather than guessed at since the format was first read. The entry it missed is **unparented** — its parent name is zero length — which the entry scanner rejected as a malformed name. Such an entry also carries its transform frame with the flag byte left at zero, so the frame's presence follows from the empty parent rather than from the flag; the writer now reproduces that instead of deriving it, which is what keeps the round trip exact.
- A zero-length parent on its own is far too weak a signal to scan on: a name followed by two zero bytes occurs inside configuration blocks constantly, and accepting those split real blocks apart in ten of the twenty rigs. What makes it safe is checking the frame that follows — the rotation must be a unit quaternion and the scale positive and finite, which float noise essentially never satisfies. The block that first exposed the entry decoded cleanly the moment the split was right, and every other rig was left untouched.
- **All twenty shipped rigs now parse, tile to their declared `entry_count`, rebuild byte for byte, and decode every configuration block** — 2,737 of 2,737, with 1,046 expression controllers recovered, and all twenty reproducing their declared `record_count` exactly. `.papr` has no unread bytes and no rejected files left.

### Added
- **`.papr` is fully decoded.** All 2,541 configuration blocks across the nineteen parsable rigs now consume exactly, from the 682 (26.8%) that matched a single canonical shape when this started, and every chain in every rig reports every byte accounted for. 906 3ds Max expression controllers come out as readable text — the rule each driven bone actually runs.
- The last two constructs: `09 03` opens a scope and sets the channel count exactly as `0a 04` does, and `01 03` is a driver list that omits the sentinel and takes `3 + channels` floats rather than `4 + channels`. They had been refused for two commits because an earlier reading had the right idea and the wrong float run, which raised coverage to 98.0% while dropping header agreement from nine rigs to seven. The correct run turned up in `B_Gluteusmaximus_L_02`, a 31-byte block with no drivers at all, where the three floats sit alone between the count and the next record.
- **All nineteen rigs now reproduce their declared `record_count` exactly**, from bear at 12 records to golem_imp_boss at 4,317. Nothing in the grammar can influence that header total, so nineteen independent agreements is the strongest statement available that these are the file's own rules. The corpus gate asserts both the full block count and the number of agreeing rigs. The manifest's `decode` grade for `.papr` moves from `partial` to `full`.

### Docs
- Rewrote the `.papr` block section of the format guide, which still described the block as opaque and the grammar as unknowable. It now carries the record table, the driver-list and bound-node layouts, three real formulas next to what they mean, and — the part worth keeping — how any of it was checked. Coverage alone proves little, because permissive rules also consume bytes; the check that counts is the header's own `record_count`, which no decoding rule can influence, and nine rigs reproduce theirs exactly. That section also records the bound-node case, where the header settled a question the byte shapes could not, and the `09 03` reading that reaches higher coverage but costs header agreement and is therefore refused.

### Added
- Took `.papr` block decoding to **2,482 of 2,541 blocks — 97.7%, from 96.1%** — and chains with every byte accounted for to 94.9%. Three small corrections, all of the same kind: bytes read as fixed zeros that are not. A bound node's lead byte is a flag that is 0 in most rigs and 1 in a few; its name is occasionally empty, meaning an unbound slot rather than a corrupt record; and a driver list may legitimately declare no drivers at all.
- The evidence for these is much stronger than coverage alone. **Nine rigs now decode end to end and all nine reproduce their declared `record_count` exactly**, up from four, and they include the large ones: golem_imp_boss at 4,317 records, machinetank and warrobot at 1,660 each, golemdragon at 891. A block this module admits it cannot read is a better answer than coverage bought at the cost of the only external check there is.

### Added

### Fixed
- Stopped the Studio freezing when Driven bones or Rig behaviour is first opened. Finding the rig files means walking the archive package tables — 1.6 million entries, about four seconds — and that was happening inline on the UI thread, so the window locked up on the click. It now runs as a generator stepped from the Qt event loop, yielding every 20,000 entries, with a progress bar in the status bar and the panel saying what it is waiting for. A worker thread was tried first and does not work: the walk is pure Python and holds the GIL, so the UI heartbeat still showed a 12-second gap; stepping it from the event loop brings that down to the cost of one package's table parse. The click itself now returns in about 2 ms.
- The result is also written to disk, so only the first session ever pays for the walk. It is under a megabyte — twenty `.papr` files and the pose-modifier descriptor — and reloads in about 6 ms, stamped with each package file's size and modification time so a game update invalidates it rather than leaving the panels showing the previous install. A damaged or stale cache is treated as a miss, never as an error.

### Added
- Decoded most of the `.papr` configuration block, which had been the opaque part of the format. It reads as a flat stream of 3-byte `(tag, type, value)` records where the type says whether a payload follows: driver lists (`u8 count`, then `u16` name and `f32` weight per driver, a sentinel, and a run of limit floats), plain name references, and — the useful one — 3ds Max expression controllers. **1,857 of 2,541 blocks now consume exactly, against the 682 that matched the single canonical 27-byte shape recognised before**: 26.8% to 73.1%. For the player rigs it turns 2 of 71 fully-decoded chains into 58 of 71, and 1 of 73 into 63 of 73, so the Driven bones tab no longer reads "partial" down the whole column.
- The expression payload is the actual rule each driven bone runs, and 894 of them now come out as text: `-Local_Euler_Z*3+30.5`, `amin(Local_Euler_Z*5.5+20) 8`, `(Local_Euler_Y-(degToRad 63.748))/2+(degToRad 63.748)`. The Driven bones detail table gained a Formula column beside Follows and Weight, because "Bip01 L Clavicle_Front follows Bip01 L UpArmTwist at 30%" is a fact and "at 1.5x its Y rotation, offset -1.7" is the thing a modder came to read. Bones that carry only an expression and no influence weight now get a row too; keying rows off weight sites alone had hidden them entirely.
- Two things keep this honest rather than fitted. A block has to be consumed to its final byte and the grammar has no per-block free parameters, so landing exactly on 1,857 block boundaries is not something arbitrary rules do; and `record_count` in the header — the total record count across every block, which nothing in the grammar can influence — is reproduced exactly for `cd_m0001_00_bear`, the one rig whose blocks all decode. The earlier attempt at this was abandoned for producing rules like "a string then ten floats then four bytes", which is not a struct anyone wrote; the difference here is that every rule is a self-validating shape (a counted list, a length-prefixed printable string) rather than a byte tally. The remaining 684 blocks stop at a handful of distinct constructs and are reported as `partial` with the offset they stopped at, never guessed past. Decoding stays strictly read-only: the writer still carries block bytes verbatim, so a misread construct cannot corrupt a file.

### Fixed
- Stopped the sculpt brushes applying one extra dab when you let go. Releasing the mouse sends a terminal phase whose only job is to close the stroke, but it carried the same brush payload as every other step and the mesh core executes before it closes — so Smooth, Inflate and Pinch sculpted once more at the release point, and a click that never moved got sculpted twice at full strength. Measured against the real core on a 16×16 grid: begin and each drag step moved 576 vertices, and so did the release. Those three tools are sample-driven — Smooth relaxes by weight alone and Inflate and Pinch take their amount from the brush radius — so an unmoved release is not self-cancelling the way a drag-driven tool's is. Grab is left exactly as it was: its displacement comes from the drag itself, so its release is already inert when the pointer has not moved and still applies the last few pixels of travel when it has. The terminator now sends zero strength, which is the one lever all four tools honour, and the release moves 0 vertices while the stroke still closes — verified by opening a second stroke straight after, which the core rejects if the first is still open. Undo continues to treat a stroke as one operation.
- Fixed the viewport's authoritative selection being thrown away on an ordinary click. Selecting a vertex, face or part asks the app what the selection should be and then applies the answer; that answer was being dropped as uncorrelated, leaving the viewport on its own optimistic guess until some later unrelated broadcast happened to refresh it. The gate deciding whether a request may be answered with a selection qualified *every* kind of request by a command name — but only the toolbar commands (Select All, Grow, Invert, Undo, and so on) carry one. A click carries a tool, not a command, so it could never qualify. Verified against the real editor by clicking, answering with a distinctive selection and reading it back: before, the viewport's selection stayed empty; after, it matches what was sent. Strokes stay excluded deliberately — a brush or transform never edits the selection, so its answer only echoes what the viewport already has, and holding a request open for each one would fill the correlation table at pointer-move rate and start evicting the real selections waiting to be rolled back.
- Kept Select All, Invert and Grow inside the geometry you can actually edit. They walked the whole document, which in a comparison session includes the untouched original loaded alongside your replacement, so they offered up vertices and faces no edit can reach; every payload the viewport sends is clamped to the editable range. Edge mode was wrong the same way, since edge topology is built across the whole document. The same commands also scanned the full edge list once per selected element, which is quadratic and freezes the window on a real game mesh rather than merely being slow; they now build the adjacency they need in a single pass.

### Added
- Added a reader, surgical editor and Rig behaviour panel for `character/descriptors/posemodifierdata/posemodifierdata.xml` — 119 KB and 2,779 settings across 98 skeletons holding the rig behaviour the game actually runs: how far a creature turns its head to look at you, how much a spine lags behind a turn, the reach and bending axis of each IK limb, wheel radii and suspension travel on every cart. Unlike `.papr` this one is demonstrably live; the engine's own `pa::engineScript::PoseModifier*` classes are named after its sections. It is deliberately not run through an XML parser: the file is eleven `<PoseModifierDataList>` roots one after another, with nine anonymous `</>` closing tags, a BOM, no declaration, and 24 comments including the Korean labels that are the only human-readable identification a vehicle block has. `ElementTree` refuses it outright, and re-serialising would fix it into strict XML, drop the comments and rewrite the hand-authored tabs — thousands of changed bytes against an engine parser whose tolerances are unknown. So the reader scans, records the character span of every value, and edits by patching spans: the shipped file round-trips byte for byte, and changing one number produces a one-byte length delta and exactly one changed setting. Scaling keeps a value's shape and its number style, so a `-45 57` range stays two numbers and `-60.0` halves to `-30.0` rather than `-30`.
- The panel keys on `.pab` skeleton, which is how the file is organised and how the Studio already identifies a character, so the player shows its 223 applicable settings rather than all 2,779. Two things it refuses to hide: one block commonly serves several characters — the player's LookAt is shared with `phw_01`, `ptm_01` and `pdem_01` — so the Applies-to column names them, because that is a consequence the file does not show; and each section can carry a `DisabledKeyList`, where an edit does nothing and explains nothing, so a banner says so. A skeleton that appears *only* in a disabled list is still selectable, since that is exactly the character whose owner needs telling — the first version keyed the picker off settings alone and made those creatures unreachable.

### Added
- Validated the prefab path rewriter against the game's own authoring tool, which is the first check on this work that does not rest on our own decoder. The archives ship thousands of prefabs that are the same asset with a single path changed — armour variants, weapon indexes — so those pairs are ground truth: rewrite vanilla A to point at B's path and the result must be byte identical to vanilla B. **15,742 of 15,750 pairs reproduce exactly, including 10,066 of 10,066 length-changing ones**, which are the cases that exercise pointer relocation, pointee length fields and the data header. The other 8 are refused as undecidable, and nothing fails. Choosing genuine pairs is most of the work and getting it wrong manufactures both false failures and false confidence: pairs must agree on the full type table including members, on every decoded object and numeric value, on all strings but one, on a file-size difference equal to that string's byte delta, and on every remaining byte once the fields a shift legitimately moves are masked. Without that last filter, `_index01` versus `_index02` variants qualify and then "fail" because the rewrite faithfully preserves A's index. `scripts/prefab_vanilla_pair_oracle.py` runs it against any extracted corpus and exits non-zero on any failure; it is mutation tested, and an earlier version of it that excused residual differences matching A was discarded after that rule hid a broken data-header patch entirely.

### Added
- Fuzzed the in-place value writer, which was the one write path the randomised testing did not cover. Path rewrites move bytes and had been fuzzed since; placements and plain values are written in place and only had example-based tests. Over the shipped archives, 501 prefabs carrying editable values took a full batch write each: every file the same size afterwards, still decoding, with exactly the requested bytes at the requested offsets and everything outside the written spans untouched. ### Docs
- Re-ran the search for a byte identifying a marker=1 group's component type, on **5,003 anchors** rather than the original 375 — the trailer fix having produced far more completed walks to anchor on. The best position now scores 14.9% against the earlier 4.0%, which looks like progress and is not: the resolved index and that byte both cluster on small values, and the agreement expected from that overlap alone is 11.8%. The reasoning was that trying one alternative at one group cannot cascade; it does, because nested groups each retry in turn and the cost multiplies down the tree. A corpus pass that normally takes about a minute had not finished in ten. Reverted.

### Docs
- Established that the prefabs which do not decode are **one problem, not eight**. The census listed eight distinct failure messages; completion turns out to track a single variable, which is how many candidate component types a file declares. With one candidate the walk completes 99.5% of the time. With two it drops to 44.7%, with three to 9.5%, and with eleven or more to about 6%. Files that fail early declare 18.8 types and 12.7 candidates on average against 5.3 and 1.6 for files that complete. The walk is essentially perfect when it has nothing to choose between, and fails as soon as it must choose — because marker=1 groups state no component type and the declaration-order fallback is a guess that is nearly free with one candidate and nearly hopeless with twelve. That explains why the messages differ while the shape does not: a wrong component means a wrong member layout, the cursor desynchronises, and whichever check trips first supplies the wording. It also explains why none of the individual causes yielded to a targeted fix and why the mask-width variants could not help. Any real gain has to come from a discriminator for marker=1 groups; nothing downstream of that choice will do it.
- Replaced the standing "the pointer test could in principle be wrong" caveat with a measurement. `value == offset + 4` cannot be proved sufficient, but it can be checked against the walk, which knows exactly which pointers it consumed: across 1,261 fully-read prefabs and **18,503 pointer sites** the two agree exactly on 99.0% of files, and 35 of the 37 sites found but never traversed open with the zero word a populated pointee begins with — which is what an unvisited pointer looks like, not a coincidence. One site went the other way and the harness can manufacture that, so it is not claimed as a genuine miss.

### Changed

### Docs
- Chased the three next-largest walk failures to a conclusion and recorded that none of them is what its message says. "Collection count N (kind N)" is not an unhandled kind: the rejected kind bytes are scattered and the bytes at the cursor are length-prefixed strings, so the walk is misaligned and reading a string as a collection header — the message invites an enumeration that does not exist. "Walk ended N bytes short" is genuinely unconsumed structure, with owner fields and object names in the leftovers, but only 37 of 729 parse as further groups when the walk resumes from the stop, so resume-parsing was tried and dropped. "Mask exceeds every candidate" fails on the first *child* group, never the root, and the child's mask needs more members than any candidate has while the root type usually would fit — but offering the root as a peer is actively worse (61.9% down to 59.4%, since it fits most masks and displaces the right component) and offering it as a last resort gains six files while relocating the failure to the same 1% progress. Building the writer forced two findings the reader had been getting away with. Flag `0x04` is not inert — it adds a second 40-byte bounds frame, and reading a fixed 80 bytes put `duration` 40 bytes late on the 18 `aim_add` bow clips that clear it; with the bit honoured they report exactly `31/30` s and every one lands on a whole frame count. And the two bytes before each float translation key are not padding: they are constant within a track, differ between tracks, match no 16 bits of the bone hash, and the same bone carries different values in different files — an uninitialised stack slot, kept per track so a rebuild can put it back.
- Added a `.paloc` reader and writer (`cdmw/core/paloc_format.py`), which is every line of text in the game: 14 language tables, 187,521 entries each. The detail that had kept it closed is that the record count is a *footer*, not a header, so a reader that opens the file looking for one finds a record immediately. All 14 shipped tables — 2,625,294 records — rebuild byte for byte, and the footer count agrees with the record walk in every one. Nothing in the format is offset-addressed or aligned, so a translated line may be any length and rewriting the table is just re-emitting the records: this is the one game format where an edit cannot corrupt anything downstream. `replace_text` is the whole of what a translation mod needs.
- Added a `.papr` reader and in-place weight editor (`cdmw/core/papr_format.py`) for the twenty constraint rigs that drive hair, cloth, tassels and the `B_Jiggle_*` chains. The per-entry record is a typed opcode stream that is *not* solved — one rig walks on the simplest reading and the other nineteen do not — so there is deliberately no `encode_papr`; a writer on a guessed grammar would emit files that load and then misbehave. What is solid is the part that matters: the driver lists are a bone name followed by an `f32` influence weight, and across the twenty rigs that locates 1,774 of them, every one a whole number between 1 and 100 and 98.6% multiples of five. Editing one is a four-byte overwrite, a no-op edit is byte-identical on all twenty, and `set_weights` refuses to write unless the caller states the value it expects to replace. This is secondary-motion tuning without touching HKX, whose structural edits stay gated.
- Added per-format decode progress to `schemas/archive_content_capabilities.v1.json`, so the answer to "can CDMW read this, can it write it, and what is left" is data rather than folklore. Every one of the 108 formats now carries where it came from (`origin`), how far it is read (`decode`), how far it can be written (`write`), what closing the gap would unlock (`priority`), a pointer to the module or corpus gate that backs the claim (`evidence`), and what is still unmodelled (`remaining`). `tools/report_format_decode_progress.py` validates the entries, recomputes the manifest's own `progress` summary, and regenerates `docs/features/format-decode-progress.md`; `tests/test_format_decode_progress.py` fails if either derived artefact drifts from the entries. Coverage is a weighted mean of the per-entry statuses rather than a file count, and the headline is reported over the 58 engine formats — 47.2% read, 25.0% write — because the 47 public formats arrive already understood and would otherwise flatter the number. Writing the entries surfaced two overclaims that the evidence rule caught: `.meshinfo` was carrying a full-decode claim over what is really a reference and field-name scrape with candidate integers, and `.pab` was carrying one despite unknown and truncated variants falling back to a best-effort scan. Both are corrected, which is why the read figure moved down.
- Added a `Carry:` control to the Placement & Animation Studio, which changes where a weapon hangs and brings its animations with it. Picking a carry position re-routes the part, moves its child socket so the item keeps the right orientation, and filters the clip browser to the draws and sheathes that start from there. Which clips those are is measured, not looked up: the action charts do name sockets and clips together, but a chart names hundreds of clips at once, so `RHand_Socket` "matches" 4,989 of them. Instead each draw is played against the rig and the hands are watched. Nearest-socket scoring does not work either — in a back draw the idle hand hangs by the hip, so the closest hand-socket pair in the clip belongs to the hand doing nothing; what separates them is how far a hand *closes* on a socket over the clip. Classification is to a body zone rather than an exact socket, because the five upper-back sockets sit within 0.06 m of each other (two of them at the same point) and the thigh sockets are nearer the hip than the two hip sockets are to each other. Of 248 draw and sheathe clips for `1_phm`, 228 are classified, split 121 hip to 107 back.
- Made a carry change able to swap the animations, the way the working mods do it. The first attempt was aimed at the wrong mechanism: an action chart names each clip as a length-prefixed full path, so retargeting one needs a replacement of exactly the same byte length, and across every chart for `1_phm` none of the 31 referenced hip draws has one — from which the tool wrongly concluded no swap was possible. The shipped `1H Sword Back Carry and Draw Animations` does not touch the charts at all: it ships a replacement `.paa` at the original clip's path, and its `cd_phm_sword_00_01_normal_stand_weapon_out_000.paa` is a byte-identical copy of the vanilla longsword draw. `EditSession.replace_clip` now does the same, and 24 of that mod's 25 replaced clips are in the measured index, so the measurement agrees with a mod known to work. Which clips to replace, and what with, are both decided by name rather than by measurement. Handedness is the dividing line and the game states it: a weapon's socket file sits under `weapon/1_onehandweapon/` or `weapon/2_twohandweapon/`, so a one-hand sword owns the `sword`, `dualsword`, `dlsd`, `swds` and `swd` families and must never touch `longsword` or `lswd` — a substring rule gets that wrong in both directions. The stand-in is the same clip name with only its family token changed, because measurement cannot answer this one: the two-hand clips measure as *hip* draws, correctly, since in vanilla the longsword hangs at the hip too, so there is no back draw to borrow. What makes a back carry read right is the two-hand weapon's animation set. Verified against the shipped mod, where six of the eight replacements having a vanilla counterpart are byte-identical copies of exactly that substitution. The swap now covers locomotion and idles, not only draws, because moving a two-hander to the hip changes how the character stands and moves while carrying it — the shipped `2H Sword Hip Carry` replaces 141 clips of which only 18 are draws. Matching the whole clip name found a counterpart for just 26% of those: take numbers and stance indices do not line up across families, so the two-hand `cd_phm_lswd_01_00_sit_std_idle_00` is the one-hand `cd_phm_swds_00_01_sit_std_idle_00`. Pairing is now by signature — the character and the descriptive words, with the family and every index number removed — which reaches 78%. The words stay exact on purpose: `walkfast_start_180_l` is a turn and `walkfast_start_l` is not, and a looser rule pairs them. Clips with no counterpart are skipped; the mod authors hand-made those. Scope is chosen rather than assumed, since pairing finds more than the shipped mods change: the dialog offers draws and put-aways alone (52 files) or the full restyle (804), with counts, and `00_mon` is left out because neither shipped mod touches it. Scope was the risk: unscoped, the swap rewrote 121 files including every boss's draw. The full list is shown for confirmation before anything is applied. User-facing text no longer refers to the specific mods the behaviour was derived from, which mean nothing to someone using the tool; the wider scope now says plainly that it covers incidental animations like eating and sitting, where the stowed weapon is still on screen. It also has its own `Swap animations...` button rather than only firing on a carry change, runs its reading on a worker with progress — decompressing one clip costs 165 ms, so the 804-file restyle took over two minutes on the UI thread and showed the window as Not Responding — and plays the result when it finishes — controlled by a `Play the new animation when this is done` tickbox in the dialog rather than a prompt afterwards — on the rig in its new placement, so the swap can actually be seen. The placement dropdown is now labelled `Hangs on:` rather than `Carry:`, which did not read as the control that moves a weapon. It no longer waits on `Match animations` — which stand-in an animation gets is decided by the weapon's handedness, not by where a draw reaches, so requiring the half-minute measurement first was gating the feature on something it does not use.
- Made the Studio say what a carry change did and did not do. Choosing a position now prints a report: where the item was carried before and now, how many draws start from each, the best draw and put-away for the new spot, and — stated plainly — that the action charts are *not* rewritten, so the game keeps playing the old draw. ### Fixed
- Fixed a weapon hanging upside down after being moved to the back. ### Added
- Added a structural `.prefab` decoder (`cdmw/core/prefab_binary.py`). A prefab is self-describing: it carries a flat table of type definitions naming every member, its declared type and its byte size, followed by a heap of pointer-addressed object records. The decoder parses that grammar rather than scavenging strings, so it recovers each scene object, its component type, which fields are actually set, and every resource path with the exact byte span that holds it. Header parsing covers 12,000/12,000 sampled archive prefabs including format versions 3 and 4 and schema revisions 13 to 15; the heap walk completes on ~93% of single-component-type files and degrades to a partial result, never a crash, on the rest. Where a prefab declares several component types, the group's component is read from the type index the element header states rather than inferred from the presence mask, which cannot tell two components apart when both accommodate it; that plus accepting every element-header marker the format uses took whole-corpus completion from 50.2% to 54.3% and the objects recovered across the corpus from 12,328 to 125,592.
- Added length-changing resource path edits (`cdmw/core/prefab_binary_edit.py`). The blob stores absolute file offsets, so resizing a string moves everything after it; the rewriter relocates every pointer and pointee length field and updates the data header. Pointers are identified by an exact property — a u32 at blob-relative `k` is a pointer if and only if it stores `blobOffset + k + 4` — rather than by scanning for values that happen to match a string offset. Verified by round-tripping 1,500 real prefabs with both longer and shorter replacements, re-decoding each and requiring the structural walk to still complete.
- Added a prefab glossary (`cdmw/domain/archives/prefab_glossary.py`) that turns declared names into plain English. `_shrinkMaskDistance` reads as "Shrink distance", `_skinnedMeshFile` as "Mesh", and each carries a line saying what it controls, so a modder can tell which fields are worth touching without knowing the engine's vocabulary. Entries were chosen by how often a field is actually set across the shipped prefabs rather than how often it is declared, and now cover 98.8% of set-field occurrences. Descriptions are inferred from each field's name and declared type, so where a name does not support a confident reading the entry carries a label only. Unknown fields fall back to de-camel-casing rather than disappearing, and engine typos are corrected in the label while the declared name stays on hover. `.pami` is classed as a mesh instance rather than a material: the files are XML `<StaticMeshInstance>` documents naming a mesh and carrying its material data, confirmed on 300 sampled files, so labelling them "Material" sent modders looking for a texture.
- Added numeric value decoding (`cdmw/domain/archives/prefab_values.py`). A `Transform` is 40 bytes holding ten floats: scale, then rotation as a quaternion, then position, with `TiledTransform` adding a tile index. That layout was measured rather than assumed -- the slice at floats[3:7] is unit-length in 74,190 of 74,225 transforms sampled from the shipped archives, and a prefab's `_worldTransform` and `_tiledTransform` agree value for value. The inspector now shows each object's world placement, opacity, flags and counts alongside its asset paths; a 1,126-object cliff scatter reads as a list of positions and rotations instead of a list of names. 143,917 numeric values are recovered across the sample corpus. Rotations are shown in degrees for reading only -- Euler angles are ambiguous, so the quaternion stays authoritative.
- Added world placement editing. Double-clicking a placement row opens an editor for position, rotation and scale; rotation is entered in degrees and converted to the stored quaternion. Transforms are fixed size, so nothing moves and no pointer needs relocating -- the file comes back the same length. Each write is checked against the bytes currently at that offset, so a stale decode is refused rather than splicing over whatever is there now, and placements are applied before path edits because path edits move bytes and would invalidate the offsets. This is the prefab's own world placement and is unrelated to Placement Studio, which retargets character attachment sockets in `.paac` and `.sockets.xml`.
- Pitched the Prefab Inspector at a modder meeting a prefab for the first time. It now opens by saying what a prefab is -- a parts list of which files an object is built from and where each part sits -- and that saving writes a separate mod package rather than touching the game files, which is the first thing anyone needs to know before clicking anything. It opens with a changeable row already selected so the action buttons are live instead of greyed until you guess a row must be picked, "repoint" became "swap for another file", and the second tab is "Fields explained" rather than "All fields".
- Reworked the Prefab Inspector's wording and states for modders. The banner leads with whether the file can be saved and counts only what the file actually holds; a read-only prefab no longer invites you to double-click things you cannot change; counts read as "1 object" rather than "1 object(s)". Collections are no longer listed as "set but with no value to show" when their contents are the rows underneath, and a tiled placement that repeats the world placement says so instead of printing the same numbers twice. Ctrl+C or right-click copies a value, full paths are available on hover, disabled buttons explain themselves, and the activity log stays hidden until it has something to report.
- Added the Prefab Inspector (Archive Browser context menu, "Open Prefab Inspector..."). One tab lists the prefab's objects with their component types, asset paths and set fields; the other lists every field the prefab declares with its type, byte size and a plain-English description of what it holds. Every value is labelled with the field it came from rather than guessed from its file extension, and the field list defaults to just the fields this prefab actually sets, since a prefab declares far more than it uses. Asset paths are editable in place and replacements are not restricted to the original byte length. Edited rows are highlighted, a running summary says how many changes are pending, and Undo puts everything back to what the file actually holds. A replacement whose file kind does not match the field it is going into is flagged -- swapping a model reference for a texture is the mistake most likely to slip through -- but flagged as a warning rather than a block, since a modder may be retargeting to an asset they are about to author. Where the archives can answer, the inspector now also checks that the replacement exists: a "Choose file..." picker lists the real archive paths of the same kind, seeded to the current file's folder so its siblings are the first thing you see, and a hand-typed path that no file matches is called out. The index is built off the UI thread before the dialog opens and cached per package root and extension (`cdmw/core/prefab_asset_catalog.py`); when no index is available the inspector claims nothing about existence rather than raising a false alarm.
- Added companion-file awareness to the Prefab Inspector (`cdmw/domain/archives/prefab_companions.py`). A prefab references only a mesh, but the engine resolves that mesh's material and physics from parallel role directories -- `character/model/.../x.pac` implies `character/modelproperty/.../x.pac_xml` and `character/bin__/meshphysics/.../x.hkx` -- so retargeting a mesh silently swaps those too. Applying a change now reports where material and physics will come from, and a replacement mesh that lacks a companion of its own is flagged before the edit is written. Measured over the shipped archives, 12,961 of 12,962 `.pac` files sit under a `/model/` directory; of those 100% have the physics companion and 99.1% the material one. When a prefab cannot be fully decoded the banner says so and editing is disabled, so an edit is never written to a file that is only partly understood.

### Fixed
- Fixed `Solid (Textured)` in the Mesh Editor leaving the viewport flat. The mode does not switch a texture on; it parks the scene on the untextured fallback, asks for the original textures to be resolved out of the archive and compiled, and waits for the resident helper to acknowledge them. That wait had a flat 20-second deadline that took no account of whether the work behind it was still running, so on a full character — where the initial scene ships with no material resources at all and every one of them has to be read and compiled on the spot — the deadline expired mid-compile and the mode was put back. The textures then landed seconds later with nothing left to complete, so the scene stayed flat for the rest of the session while the helper was holding exactly the materials that had been asked for. An interval that ends with the compiler still busy now buys another one, up to nine, and a material acknowledgement that arrives after the wait was abandoned re-applies the mode it was abandoned for. Choosing any other Mesh view in the meantime cancels that, so nothing snaps back over a deliberate choice, and a session that ends forgets it.
- Fixed the `Preparing Alignment` window that appears while the Mesh Replacement Builder opens showing as a blank white box. It is a progress dialog, and it reports each construction step, but nothing ever drew it: `QProgressDialog` only pumps events for itself while it is modal, this one is deliberately not, and Builder construction never yields between showing it and finishing. Until the platform has delivered the expose event the window has no backing store and `repaint()` does nothing, so the first pass now lets Qt run once — with user input excluded, which keeps a stray click or key away from the half-built dialog behind it — and every step after that repaints synchronously.

### Fixed
- Fixed the embedded .NET mesh editor and 3D preview flashing on screen while they start. The helper's window was created as a borderless top-level window at screen (0, 0) and only reparented into the workbench pane once startup finished, so opening Mesh Editor or Edit Mesh put a stray window in the corner of the monitor and let you watch WinForms assemble the editor inside it a panel at a time. The window is now created as a child of the host pane from the outset and stays hidden until its control tree is realised and it is verified in the host, so the workbench's own "starting" panel covers the whole stretch and the editor appears complete in one step. Nothing is reparented after the fact, which also removes a cross-process `SetParent` that could fail with Win32 5023.
- Fixed the Mesh view control sitting on "Solid (Textured)" while the viewport stayed grey. Picking that mode parks the viewport on the untextured fallback and waits for a resident material acknowledgement, but the resolver it calls returned silently whenever the textures were already marked loaded, so no material update was sent, no acknowledgement arrived, and the pending flag was never cleared. The resolver now reports what it did (started / in flight / already loaded / unavailable) and republishes resolved materials; the request completes when the helper already holds them, fails with a status message when there are none, and otherwise arms a 20-second watchdog so the control can never report a mode the viewport is not in.
- Fixed the Edit Mesh grid disappearing. Each renderer pane draws from its own presentation context but only the active one was written back, so in side-by-side the two drifted and a pane could keep or lose a grid nobody asked it to; separately, replacing the resident package reseeded grid visibility from the incoming package's `dotnet_scene.json`, and the two package builders disagree about the default. Grid and gizmo visibility are now host-owned, fanned out to every context, and preserved across package swaps.
- Fixed the Edit Mesh tool rail collapsing to the Classic panel widths. An embedded scene update arriving with mesh edit already on re-ran the reveal path, which uncollapsed the flanks against the classic saved widths while the layout switch early-returned as already active, dropping the rail's 340 px property column to the classic 256 px minimum and the scene inspector to 360, where the tool pages no longer fit. Both paths now re-assert the active layout's own dock width. Entering and leaving mesh edit never reproduced this; only the redundant same-mode update did.
- Fixed Edit Mesh button captions painting over their neighbours - "Bind Selected Parts" ran under "Clear Refit" even at the full rail width - by reflowing equal-percent rows onto extra rows when a column cannot seat them side by side, and wrapping the Morph diagnostic at the column width instead of a hardcoded 460 px. The status footer is one line with the full text in its tooltip, which gives that height back to the viewport and tool columns.
- Fixed exported OBJ material libraries losing every texture binding. `export_archive_mesh` still passed the leading `texconv_path` argument that the native texture backend change removed, so the call raised `TypeError`, the texture manifest came back empty, and every `map_Kd` kept the bare placeholder name. The textures were copied into `referenced_files/` but never bound, so an OBJ opened untextured with its textures sitting right beside it. Every export from the Archive Browser took this path. The shared 120-line `except` that covered the preview rebuild, the MTL rebinding, and the manifest write now names the stage that failed, which is why a broken texture pipeline read as a manifest warning for ten days.
- Fixed packed roughness/metal maps binding to the specular slot instead of the material slot. `SkinnedMeshStandard` writes its packed map to `_materialTexture` but still names the file `_sp.dds`, and the role classifier matched the file suffix before the authored parameter, so the material slot resolved to null and the response fell through to the legacy specular/gloss path - metal rendered flat in Archive Browser preview. The authored parameter now outranks the suffix, keeping the skin carve-out that reads `_sp.dds` as specular. The Mesh Editor package hid this because it synthesizes separate channel files; only the archive package, which hands the renderer raw archive DDS, stranded the map.
- Fixed the base colour of layered PAC materials coming from the wrong textures. `_grimeDiffuseTexture{R,G,B}` are the three colour layers `_colorBlendingMaskTexture` selects, so they are the surface colour, while `_detailDiffuseMask*` are overlays; the visible-layer base fallback ranked detail above grime, handing the base slot to an overlay whenever both were declared. Separately the layer palette preferred `_scratchTintColor*` - the low-alpha wear accent - over the authored `_tintColor*`, and one chromatic scratch channel was enough to keep all three, so a sword blade rendered near-white and its grip yellow instead of the authored gold and brown. Both selectors now prefer the authored tint and fall back to scratch only where a channel declares none.
- Fixed layer dyes being resolved by substring. The tint lookup matched candidate names with a substring helper while the candidate list encodes a precedence, and `tintcolorr` is a substring of `scratchtintcolorr`, so any layer asking for its primary dye silently received the scratch dye whenever both were declared - on one real axe that swapped a neutral tint for a cyan one and rendered the steel head blue-teal.
- Fixed `_sp` channels being decoded the same way for every shader family. Disassembling the shipped shader cache shows R is never sampled outside skin and the layout differs per family: Standard/Cloth/Fur sample G roughness and B metalness, Skin adds R subsurface, and Hair samples G alone with no metal channel at all. Feeding R into ambient occlusion was a live bug rather than a stale comment - `_sp` files are BC1 and plenty ship R authored flat dark, so those assets rendered fully occluded. Skin roughness also read G inverted, the hair strand sheen constant was dead code that the affine table short-circuited past, and `SkinnedMeshFur` was classified as hair, which discarded its metal channel.
- Fixed preview colour and material response being driven by category guesses instead of the source maps. The dominant `_sp` decode read three of four channels wrongly - R is occlusion, so `1.0 - r * 0.22` darkened every surface by a fifth; A is an opaque control value, so `a * 0.52` gave every texel 0.64 reflectance and was the main source of shine on cloth and leather; and a `* 0.58` factor capped a fully metal texel at 0.51. Layer maps carry mask coverage in alpha and are composited in priority order, but coverage was lost and the layers were weight-averaged, pinning every roughness map near a constant 0.58. In the renderer, source normals are BC5 so the sampled blue channel is always 0 and every normal pointed into the surface - Z is now rebuilt from XY; reflectance comes from the metal fraction rather than a specular map, so dielectrics cannot inherit a metallic sheen; and category caps and floors apply only where no map is bound, so a cloth family keeps the authored per-texel metal that garments carry as studs and trim. Verified with the GPU parity report at 38/38 and by rendering 43 real weapon and armour assets plus the 15-asset material regression corpus.
- Fixed a flat specular floor on the second most used decode path. `standard_v2_detail` multiplied its specular by an alpha that is opaque on the detail mask, making it a flat `+0.20` on every texel - a guaranteed 0.28 floor, which is why cloth and leather read as if they had been waxed. The term is gone and the floor returns to the plain dielectric 0.04. The hair sheen was likewise a constant pretending to be data-driven, built from a variance that saturated so every shipped hair asset resolved to the same value; it is now one named constant with its reason recorded.
- Fixed the recolour operator being damped to roughly 5% on metal-classified submeshes - most weapons and armour - so a saturated colour rendered as a wash while the CPU bake repainted fully. The damping is now gated on whether a base tint was authored, making the authored path identical to the bake. Measured on a real sword blade: chroma 4.6 damped against 15.9 authored.
- Fixed glow colour and strength refusing any selection other than a single part, which left multi-part glow selections unauthorable with no way forward.
